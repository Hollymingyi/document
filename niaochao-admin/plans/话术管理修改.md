# Plan: 话术执行流程对齐 Plan §4.6

## Context

对比 `plans/04-话术管理.md` §4.6 与 gt-call 当前实现，发现 3 处偏差：
1. VAD 前置音检测完全缺失 — 接通后立即起播，与 plan 要求的"等前置音结束再播放"不符
2. 转接超时不一致 — plan 要求 30 秒，当前用 60~180 秒
3. `transfer_status` / `last_failure_reason` 枚举缺失 — 当前没有细粒度的转接失败原因

按优先级实现：Gap 1 → Gap 3 → Gap 2。

---

## Task 1: VAD 前置音检测

### 新建 `PreToneDetector`

`gt-call/src/main/java/pro/skymind/cc/vs/service/PreToneDetector.java`

```
- 字段: silenceGateMs, maxWaitMs, silenceThreshold
- Per-stream state: ConcurrentHashMap<streamId, DetectionState>
  - DetectionState: consecutiveSilenceMs, startTimeMs, callback, scheduledFuture(maxWait timer)
- startDetection(streamId, Runnable onComplete): 注册检测 + 启动 maxWait 定时器
- onAudioChunk(streamId, byte[] pcm): 计算 RMS, 判定静音/活动帧, 连续静音 >= gateMs 时触发 callback
- cancel(streamId): 清理
- computeRms(): 复用 UdpAsrSidecar 的实现
```

### 配置项

在 `SpeechRuntimeProperties.InterruptProperties` 添加内部类：

```java
public static class PreToneProperties {
    private boolean enabled = true;
    private long silenceGateMs = 1000;     // 连续静音判定时长
    private long maxWaitMs = 5000;         // 最大等待兜底
    private int silenceThreshold = 300;    // RMS 静音阈值
}
```

### 集成点

**`UdpAsrSidecar.senderLoop()`** (~line 410):
- 在 `if (sess.suppressed)` 判断之前，检查 `PreToneDetector` 是否对该 streamId 有活跃检测
- 如果有：计算 RMS → `preToneDetector.onAudioChunk()` → 不发送 ASR → 当检测完成后自动切换到正常 ASR 流程
- 如果没有：保持现有逻辑不变

**`OutboundBotCallModeHandler.handleChannelPark()`** (~line 363):
- 在 `if (shouldPlayOpening)` 代码块内、现有播放逻辑之前：
  - 如果 `preToneDetector` enabled → `preToneDetector.startDetection(streamId, () -> proceedWithPlayback(s))` 并 return
  - `proceedWithPlayback()` 包含现有的 file mode / TTS mode 播放逻辑
- 如果 disabled → 直接走现有逻辑（向后兼容）

**文件涉及**:
- `UdpAsrSidecar.java` — senderLoop 添加 pre-tone 检测分支
- `OutboundBotCallModeHandler.java` — handleChannelPark 延迟播放
- `SpeechRuntimeProperties.java` — 添加 PreToneProperties 配置
- `PreToneDetector.java` — 新建

## Task 2: transfer_status / last_failure_reason

### CallMetrics 扩展

`CallMetrics.java` 添加字段：
```java
private volatile String transferFailReason;  // agent_no_pickup / no_idle_agent / network_error
```

### 设置时机

| 位置 | 场景 | transferFailReason |
|------|------|-------------------|
| `AcdQueueService.onQueueTimeout()` | 队列超时 | `"agent_no_pickup"` |
| `AcdQueueService.requestAgent()` 返回 false | 无空闲坐席 | `"no_idle_agent"` |
| `AcdBridgeService.bridgeToAgent()` bridge 失败 | 网络异常 | `"network_error"` |

### TalkInfoCallbackDTO 添加字段

```java
private String transferStatus;       // not_triggered / succeeded / failed
private String lastFailureReason;    // customer_mid_hangup / agent_no_pickup / no_idle_agent / network_error
```

### TalkInfoCallbackBuilder 映射逻辑

在 `build()` 方法中：
```
transferStatus:
  cm.transferResult == "success"  → "succeeded"
  cm.transferResult in ["fail","busy"] → "failed"
  cm.transferResult == null 且 s.isTtsMode==false → "not_triggered" (不转接类)
  cm.transferResult == null 且 fileMode 且 customer mid-hangup → "not_triggered"
  其他 → "not_triggered"

lastFailureReason:
  customer mid-hangup (hangupBy=="customer" 且 transferResult==null) → "customer_mid_hangup"
  cm.transferFailReason 不为空 → 直接透传 (agent_no_pickup / no_idle_agent / network_error)
  其他 → null
```

### 文件涉及

- `CallMetrics.java` — 添加 transferFailReason
- `TalkInfoCallbackDTO.java` — 添加 transferStatus + lastFailureReason
- `TalkInfoCallbackBuilder.java` — 映射逻辑
- `AcdQueueService.java` — 设置 transferFailReason
- `AcdBridgeService.java` — 设置 transferFailReason
